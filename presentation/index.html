Wordwall testing codebase

ÉTAT INITIAL — 100% Spring Framework
  • Sans Spring : new Controller(new Service(new Repository())) → couplage fort
  • Changer d'impl oblige à modifier le code appelant
  • Tester en isolation est impossible sans instancier toute la chaîne
IoC (Inversion of Control)
  • Ce n'est plus le code qui crée ses dépendances — c'est le conteneur
  • Le Controller déclare son besoin, Spring fournit l'instance
  • Contrôle transféré du code métier vers le conteneur
Component Scan — Spring Framework
  • @ComponentScan scanne les packages à la recherche de stéréotypes
  • Stéréotypes : @Component, @Service, @Repository, @Controller
  • Spring enregistre les définitions de beans — sans encore les instancier
  • ⚠ Pas encore Spring Boot ici : @ComponentScan est 100% Spring Framework
ApplicationContext — Spring Framework
  • Le conteneur IoC qui gère le cycle de vie de tous les beans
  • Bien plus qu'une map : scopes, événements, @PostConstruct / @PreDestroy
  • Scope singleton par défaut → une seule instance partagée entre tous
Auto-Configuration — Spring Boot
  • C'est ici qu'on passe de Spring Framework à Spring Boot
  • @SpringBootApplication détecte les dépendances du classpath
  • spring-data-jpa présent → DataSource + EntityManagerFactory configurés auto
  • spring-security présent → filtre de sécurité activé auto
  • @ConditionalOnMissingBean : le dev surcharge uniquement ce qu'il veut
  • Pattern "starter" : une dépendance = une auto-configuration
Résolution du graphe de dépendances
  • Spring n'instancie pas les beans dans l'ordre du code
  • Il analyse le graphe, instancie les feuilles d'abord (sans dépendances)
  • Remonte le graphe jusqu'aux beans qui dépendent de tout le reste
  • Cycle A→B→A détecté au démarrage → exception claire
  • Injection par constructeur rend les dépendances explicites et vérifiables
@SpringBootTest — transition vers le slide suivant
  • Rejoue TOUT ce qu'on vient de voir : scan + graphe + auto-config + infra
  • Puissant pour les tests d'intégration E2E
  • ❓ Question à poser : "A-t-on besoin de tout ça pour tester un seul endpoint ?"
  • → Transition vers le Slice Testing

ÉTAT INITIAL — @SpringBootTest : tout le graphe
  • @SpringBootTest charge TOUT le mécanisme Spring
  • Nécessaire pour les tests E2E — mais excessif pour la majorité des tests
  • ❓ "A-t-on besoin de charger la DB pour tester qu'un endpoint renvoie 400 ?"
  • → L'idée du slice testing : ne charger que la tranche nécessaire
Les 3 couches
  • L'application est organisée en couches, chacune avec ses propres beans Spring
  • Web : Controllers, Filters, ControllerAdvice, Jackson, Security
  • Métier : logique métier — idéalement sans dépendance Spring
  • Persistence : Repositories, JdbcTemplate, DataSource, Flyway
  • Spring Boot propose une annotation de slice pour chaque couche
@WebMvcTest
  • Charge uniquement la couche Web — pas de Services, pas de DB
  • Dépendances manquantes simulées avec @MockitoBean
  • Pas de serveur HTTP réel — MockMvc simule les requêtes en mémoire
  • Cas d'usage : codes HTTP, sérialisation JSON, @ControllerAdvice, filtres sécurité
Couche Métier : pas de slice Spring dédiée
  • Le code métier bien conçu n'a pas de dépendance Spring
  • Injection par constructeur → testable directement avec JUnit + Mockito
  • Pas besoin de démarrer un contexte Spring → test unitaire, le plus rapide
  • ⚠ Si votre code métier dépend de Spring → signe d'architecture à revoir
@JdbcTest
  • Charge uniquement la couche Persistence — pas de Controllers, pas de Services
  • DataSource + JdbcTemplate ; ici Testcontainers PostgreSQL pour une vraie DB
  • Transactions rollback-ées automatiquement → tests indépendants, pas de pollution
  • Cas d'usage : requêtes SQL natives, mappings RowMapper, contraintes DB, migrations Flyway
Autres slices
  • @RestClientTest → clients HTTP sortants (RestTemplate, RestClient)
  • @JsonTest → sérialisation/désérialisation JSON uniquement
  • Principe identique pour tous : charger le minimum nécessaire
Clôture

MockWebServer & enqueue :
  • MockWebServer = vrai serveur HTTP local (okhttp). Ici, le démarrage/arrêt et le branchement sur le client sont déjà fournis.
  • enqueue(MockResponse) empile les réponses dans une file FIFO : chaque requête entrante consomme la suivante (200 → 404 → 500…).
  • Le body = le JSON résultat (helper de lecture fourni). String.formatted(...) aide à injecter des valeurs dans un gabarit JSON.
  • 1 dépendance : com.squareup.okhttp3:mockwebserver (déjà au pom).

Refacto 3 — Testcontainers PostgreSQL. Branche atelier/3-testcontainers.
  • Pourquoi quitter H2 : H2 en mode PG est une simulation. Requêtes natives, types, index, migrations Flyway peuvent passer en H2 et casser en PG réel.
  • jdbc:tc:postgresql:16:///dino : le driver Testcontainers s'interpose et démarre un container à la 1re connexion JDBC — il suffit de changer l'URL.
  • La dépendance qui active jdbc:tc: est org.testcontainers:postgresql : elle embarque transitivement org.testcontainers:jdbc (le driver du schéma jdbc:tc:). Ce n'est PAS spring-boot-testcontainers / @ServiceConnection, qui relève de l'approche programmatique.
  • @AutoConfigureTestDatabase(replace = NONE) sur @JdbcTest : sinon Spring remplace la datasource par une base embarquée.

Les 3 services métier — la chaîne d'assignation.
  • DinoAssignmentService : le chef d'orchestre. Reçoit un dino, cherche le premier enclos adapté (climat, habitat, surface/eau/nourriture) et persiste. S'appuie sur ParcRepository pour les données.
  • DinoSpeciesService : traduit un dino en espèce + ses besoins (surface, eau, nourriture), en croisant l'API externe et le registre local JSON.
  • DinoTypeService : adaptateur de l'API REST externe (UUID → type/espèce) ; transforme un 404 en Optional.empty().
  • Sens de la dépendance : Assignment → Species → Type, chaîne linéaire, sans cycle. C'est DinoAssignmentService qui porte la logique parc/enclos — clé pour comprendre le BUG-1042 qui suit.

Refacto 4 — BUG-1042. Départ atelier/4 (test vert, bug NON reproduit).
  • Symptôme prod : un T-Rex (200 m² requis) est affecté à un enclos forêt de 220 m² qui héberge déjà un Velociraptor (50 m²). 220 − 50 = 170 < 200 : l'enclos aurait dû être refusé.
  • Cause : les ressources consommées par les dinos déjà présents sont ignorées. Le bug n'apparaît que si l'enclos contient déjà un dino.
  • Mission : un test avec des mocks reste vert (on stubbe ce qu'on croit vrai) ; en passant la couche service en réel (sans Spring), le bug se reproduit, puis on corrige.

Tests d'intégration — atelier/7-it. On valide des scénarios métier de bout en bout, à travers le vrai point d'entrée technique (l'API REST), en isolant uniquement les dépendances externes via Testcontainers / MockWebServer. Approche boîte noire : on n'inspecte pas l'intérieur, on caractérise la réponse.

Tests d'intégration — un exemple

Principes
  • Testcontainers / MockWebServer pour les dépendances externes
  • On passe par les points d'entrée technique (l'API REST dans notre exemple) pour exécuter nos scénarios métier
  • Test en mode « boîte noire » : on envoie des données et on caractérise ce que l'on reçoit via comparaison JSON
